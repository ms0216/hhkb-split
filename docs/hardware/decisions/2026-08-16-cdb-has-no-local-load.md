# 2026-08-16 調査 C_DB は「負荷の直近にいないパスコン」だった（削除できる）

> **ファイル名は `cdb-has-no-local-load` のままだが、正確には
> 「no local load」ではなく「負荷はいるが、その直近が C_DB ではない」。**
> 初版の理由づけが誤っていた名残（下の警告を読むこと）。

**調査結果。まだ削除していない。**`C_DB`（0.1µF・C49678・0805）は
子基板の 3V3 に載っているが、**その 3V3 に急な電流を要求する負荷は、
すべて XIAO の内部にいて、内部のパスコン群のほうが C_DB より
桁違いに近い**ことが分かった。**C_DB の取り分は誤差**なので削除できる。

**覆した結論**: #40「XIAO → C_DB」（各 IC が自分の直近パスコンを持って
いるから C_RAIL を消してよい、という論拠の一部）。
**C_DB は「XIAO のパスコン」ではなかった。**XIAO はモジュールで、
**負荷（nRF52840）も、それを見るパスコンも、両方とも内部にいる。**

> ### ⚠️ この文書は理由づけを 1 度書き直している（2026-08-16・利用者の指摘）
>
> **初版はここに「3V3 に電流を引く能動部品が子基板上に 1 つも無い」
> 「XIAO は 3V3 の供給側で、負荷ではない」と書いていた。これは誤り。**
>
> **USB 駆動時しか見ていなかった。**電池駆動時は
> `電池 → SW_PWR → D_PWR → V3V3 → XIAO` で、**3V3 は XIAO への入口**。
> その先の nRF52840 は BLE 送信で電流をステップさせる**実在の負荷**である
> （`circuit.py:496` の `D_PWR: A=VBATT_SW, K=V3V3`）。
>
> | | 3V3 の向き | XIAO は |
> |---|---|---|
> | USB 駆動 | 内部 LDO が生成し**外へ出る** | 供給側 |
> | **電池駆動** | ショットキー経由で**中へ入る** | **負荷側** |
>
> **結論（削除できる）は変わらないが、根拠は下のとおり差し替えた。**
> 片方の動作モードだけ確かめて全体のように言った——この案件で
> 繰り返し出ている型そのもの（`never-report-a-named-subset-as-the-whole`）。

### 正しい理由づけ — 「相手がいない」ではなく「取り分が誤差」

```
        ┌─ C_DB（0.1µF）… XIAO の外側
        │
D_PWR ──┴──── XIAO の 3V3 ピン
                    │  ← ここから内側は XIAO の中
                    ├─ 2.2µF ×5（内部・分散配置）
                    └─ nRF52840（負荷。急な電流はここが要求する）
```

**電流は「近い順」に取られるのではなく、全供給元から同時に、
ループインダクタンスに反比例して分流する。**C_DB も流していないわけ
ではない——**取り分が数 % 以下で、誤差になる**というだけ。

**したがって「閾値」は無い。**もし C_DB が内部の 5 個と同じ距離に置けたなら
同格に効く。効かないのは**外側だから**ではなく、**ループ長の差が桁違い**だから。

そして**足りているところに数 % を足しても改善しない**一方、**もし内部が
不足していたなら数 % では救えない**。**どちらに転んでも C_DB の出番が無い。**

**きっかけは利用者の指摘**（2026-08-16）:

> 外に出る 3V3 を守るために、595 のパスコンがあるのでは？
> 595 を守るために、595 から遠い C_DB がある意味は？
> XIAO 内部の、調査してくれたコンデンサたちがパスコンなのでは？

**両方とも正しかった。**

|---|---|---|---|

| `D_PWR` | (151.51, 90.45) | `1` | ショットキー。**電池はここから 3V3 へ入る**（`A=VBATT_SW, K=V3V3`） |

| `J_MAIN` | (150.00, 111.0) | `2` | FFC で主基板の 595 へ渡す |

**3V3 ネットの全パッド（20 パッド / 12 部品・全数）:**

| 部品 | 値 | 位置づけ |
|---|---|---|
| U6 SGM2040-3.3YUDH4G | 3.3V / 250mA LDO | **3V3 の発生源**（pad 1 = OUT） |
| **C3 / C6 / C29 / C39 / C41** | **2.2µF ×5** | **LDO の出力容量。公称 合計 11µF** |
| U1 NRF52840_QF | — | **唯一の実負荷**（6 パッド） |
| R13 / R5 | 10k / 2.2k | プルアップ等 |

| U7 | **DNP** | 未実装 |
| U4 XIAO-nRF52840 | — | モジュール外形（3V3 の出口） |

C4(2.2µF) は VIN 側で**別ネット**。C34/C42 は `DEC4-6`、C24/C35 は RF 系で、
いずれも 3V3 ネットではない（**版 1・2 はここを混ぜていた**）。

> **⚠️ 「合計 11µF」と足し算で読まないこと。効いているのは並列であること。**
>
> パスコンとしての速さを決めるのは容量ではなく **ESL（等価直列
> インダクタンス）**で、これは**並列にすると下がる**（5 個なら約 1/5）。
>
> | | 容量 | ESL | ns 級に応えられるか |
> |---|---|---|---|
> | 11µF **1 個**（大パッケージ） | 11µF | 大 | **応えられない** |
> | **2.2µF ×5（分散）** | 11µF | **約 1/5** | **応えられる** |
>
> **同じ 11µF でも中身が違う。**Seeed が 1 個にせず 5 個へ散らしているのは
> この定石。**LDO の安定条件（§4-1）には合計値が効き、nRF52840 の
> パスコンとしては並列数が効く**——2 つは別の話で、両方とも満たされている。

**XIAO 内部の 3.3V レールに載っている実負荷は nRF52840（U1）だけで、
そのパスコンは内部に全部揃っている。**3V3 に 2.2µF が 5 個並列で載り、
別ネットの `DEC4-6`（C34/C42）が nRF52840 の内部レギュレータを見ている。

**負荷が内部にいて、そのパスコンも内部にある。**
外から 0.1µF を 1 個足しても、分流の取り分は誤差にしかならない。

## 3. なぜ C_DB は 595 の役に立たないか

595（`U1` / `U2`）と `C_U1` / `C_U2` は**主基板側**にある。
子基板の部品は `BT1_-` `C_DB` `D_PWR` `H1` `H2` `J_MAIN` `R_HI` `R_LO`
`SW_PWR_1` `U_MCU` の 10 点で、595 は含まれない。

595 のスイッチングのリターン電流は、`C_U1` / `C_U2` が**主基板上で
局所的に閉じる**。閉じきれなかったぶんだけが FFC を遡ってくるが、

```
C_DB の自己共振      約 19MHz
FFC 12 芯・数十 mm   直列インダクタンスが挟まる
```

**ns 級のループは FFC を渡れない。**C_DB は 595 のエッジに対して
事実上見えていない。**「595 から遠いパスコン」は 595 を守らない。**

> ⚠️ **2026-08-16 追記 — 結論は正しいが、この理由づけは不正確だった。**
> 桁を出した（[2026-08-16-ffc-loop-inductance.md](2026-08-16-ffc-loop-inductance.md)）。
> XIAO 3V3_OUT → 595 の直列 L は **約 145nH** で、595 のエッジ（knee 167MHz）
> に対する分流比は **C_U1 : FFC 経路 = 1 : 58**。**渡ってこないのは事実。**
> ただし **FFC 単体は 64nH で全体の 4 割にすぎず**、残りは両基板の
> 0.2mm 幅 V3V3 配線（97mm）である。**FFC を 0mm にしても結論は動かない。**
> つまりこの節が本当に依拠しているのは「FFC が大きいこと」ではなく、
> **「595 が自分の直近に C_U1 を持っていること」**である。

パスコンで効くのは距離ではなく**往復ループ長**（`decoupling-cap-is-loop-length-not-distance`）。
C_DB のループ長 4.49mm は XIAO の 3V3/GND パッドに対する値で、
595 に対しては FFC ぶんが丸ごと乗る。

## 4. LDO の負荷過渡は C_DB では担えない

残る可能性は「595 の消費電流がステップで変化したとき、FFC 越しの
負荷変動に対して SGM2040 の出力が振れる」ぶん。**これも C_DB の
担当ではない。**

| | 帯域 | C_DB(0.1µF) は効くか |
|---|---|---|
| LDO のループ帯域 | 数十〜数百 kHz | **効かない**（19MHz 品） |
| ここに効かせるなら | µF 級が必要 | **#44 で「守る相手が実在しない」と実測済み** |

二重に、C_DB が埋められる穴ではない。

### 4-1. SGM2040 の出力容量は XIAO 内部で満たされている（2026-08-16 追記）

**この節にはもともと穴があった。**「負荷が近くにいない」は
「**LDO 自身が外部の出力容量を安定条件として当てにしていないか**」を
別に確かめないと削除の根拠にならない。C_DB は XIAO の 3V3_OUT 直近＝
**LDO 出力の直近でもある**からで、そこは埋めた。

出典: [SGM2040 データシート](https://www.sg-micro.com/rect/assets/9d7e04e6-7450-4c5c-b94c-fa500b90b628/SGM2040.pdf)
（SG Micro・18 ページ）。XIAO 実装品 `SGM2040-3.3YUDH4G/TR` と**型番が完全一致**
（Ordering Information の UTDFN-1×1-4AL 版）。

| 出どころ | 規定 |
|---|---|
| Recommended Operating Conditions | Output Effective Capacitance, C_OUT = **0.1µF 〜 10µF** |
| OUT ピン説明 | 「effective capacitance in the range of 0.1µF to 10µF **to ensure stability**」「**as close as possible to OUT pin**」 |
| Application Information | 「0.22µF or larger X7R/X5R」「**minimum effective capacitance of C_OUT that SGM2040 can remain stable is 0.1µF**」 |

**§2 の 2.2µF ×5（公称 11µF）が、これを内部で満たしている。**

| | 判定 |
|---|---|
| 安定条件 | 公称 11µF。**下限 0.1µF に対し 100 倍以上。C_DB は安定性に不要** |
| 上限側 | **公称値では 10µF 上限を既に超えている。**C_DB(0.1µF) を足す余地はどこにも無い——**足す側が危ない** |
| DC バイアス減衰（§8 の懸念） | **むしろ好都合。**実効値は公称より下がるので 10µF 上限側に収まる。下限 0.1µF に対しては 5 個並列ぶんの余裕がある |

⚠️ **上限側は公称値で超えている**が、SG Micro が XIAO のような
使い方を想定していないとは考えにくく、実効値（DC バイアス・温度で目減り）
では収まっている公算が大きい。**いずれにせよ C_DB を足す方向の議論は
成立しない**ので、削除の判断には影響しない。

**C_DB は、その 5 個並列に 6 個目を足す行為。**C_RAIL が C_U1 の重複だったのと同じ形（§5）で、
今回はそれが**外部データシートで裏を取れている**。

## 5. #40 との関係 — **同じ性質のものが、もう 1 つ残っていた**

#40 で `C_RAIL` を消したときの論拠はこうだった:

> 削除した理由は「不要と証明できたから」ではない。必要と言える根拠が
> 1 つも無く、**各 IC が既に自分の直近パスコンを持っているから**
> （595 → C_U1/C_U2、**XIAO → C_DB**、レール → C_BULK 100µF）

**この括弧の中の「XIAO → C_DB」が誤りだった。**XIAO は IC ではなく
モジュールで、パスコンは内蔵している。C_DB は XIAO の外側に付いた
**重複**であって、C_RAIL が C_U1 の重複だったのとまったく同じ形。

| | C_RAIL（#40 で削除） | **C_DB（今回）** |
|---|---|---|
| 名目上の役割 | ケーブル入口の高周波を落とす | XIAO のパスコン |
| 実際 | C_U1 の 5.1mm 隣＝重複 | **XIAO 内蔵の 2.2µF ×5 の重複。負荷はいるが、その直近は内部の 5 個** |
| 削除の論拠 | 必要と言える根拠が無い | 同上 |

## 6. #44（バルク削除）との関係

**別件。#44 が消したのは µs 級を担当する `C_BULK` で、根拠は
「BLE の最大瞬間風速が実在しなかった」という実測だった。**

今回の根拠は電流ではなく**トポロジ**（負荷が近傍に無い）。
#44 の §6「パスコンは残る・役割が違う」は**バルクとパスコンの
役割の違いについては今も有効**だが、**C_DB が守っている相手が
誰なのかは #44 では検証していない。**そこが今回埋まった。

## 7. 結論と、まだやっていないこと

**C_DB は削除できる。**根拠は 2 つで、**両方とも外部の事実で裏が取れている**:

1. **3V3 の負荷は 2 つとも子基板の外にいて**（XIAO 内部の nRF52840・
   主基板の 595）、**どちらも自分の直近に別のパスコンを持っている**。
   C_DB は両方に対して外側で、**分流の取り分が誤差**（§1・§2・§3）
2. **LDO の安定条件も XIAO 内部で満たされている**（§4-1・データシートの
   C_OUT 規定と内部の 2.2µF ×5＝公称 11µF）

実装部品が **2 個減る**（左右の子基板に 1 個ずつ）。

**⚠️ この文書は調査結果であって、まだ何も消していない。**
削除するなら #40 と同じ手順で、**消した名前で grep して 3 つを揃える**
（CLAUDE.md の作法 8）:

| | 触るもの |
|---|---|
| コード | `tools/circuit.py:599` のネットリスト、`tools/gen_daughterboard.py` の配置（`c.SetReference("C_DB")` 周辺・`SILK_REF` の 739 行目）、`tools/gen_sch.py:105` と `:472` |
| 検査 | `test_every_ic_has_a_decoupling_capacitor` の `ICS`（`circuit.py`）から `xiao_nrf52840` を外す。**「モジュール内蔵で充足」を記録として残す**——外すだけだと、次に誰かが「XIAO にパスコンが無い」と言って足し直す |
| 生成物 | `pcb/hhkb_split_daughterboard.kicad_pcb`、`pcb/unrouted/...`、`.kicad_sch`、`pcb/drc_daughterboard.json`、`pcb/route_daughterboard.json` |
| 記録 | この文書、`open-gaps.md` #40 の「XIAO → C_DB」、`parts-audit.md` §5、`decisions/2026-08-16-remove-bulk-cap.md` §6 の「パスコンは全部残る」 |

**壊し方の検査**（作法 2）は「C_DB が復活していないこと」ではない。

⚠️ **初版はここを「3V3 に子基板側の負荷が増えていないこと」と書いていたが、
これも「負荷が無い」という誤った前提の上に載っていた**（負荷は最初から
2 つあり、どちらも板の外にいる）。**正しくは:**

> **「子基板の板の上に、自分の直近パスコンを持たない能動部品が
> 現れていないこと」**

**数えるべきは負荷の有無ではなく、「その負荷の直近に誰かいるか」。**
