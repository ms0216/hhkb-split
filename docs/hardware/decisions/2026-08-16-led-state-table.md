# LED の表示を、通信の状態から定義する（2026-08-16）

## なぜ書くか

**利用者の指摘:**

> 通信の状態と LED の状態は、基本的に合わせておくべきだと思います。
> 出荷直後状態＝まだ左右がボンディングされていない・PC とも繋がっていない時、
> どういう挙動を現状しますか？また、どういう挙動が期待ですか？
> **それを定義できていますか？**

**定義できていなかった。** 最初の実装は「見せたい 3 パターン」を決めて、
残りを `default` に流しただけだった。CLAUDE.md の
「**効く条件を全部列挙してから、候補を並べる**」を破っている。

その結果、**出荷直後（未ボンド・PC 未接続）に左が緑しか出さない**という
穴があった。左は「右とも繋がっていない・PC とも繋がっていない」という
二重の未接続なのに、優先順位で青が潰れて片方しか見えない。

**もう 1 つの指摘:**

> 接続した瞬間一秒点灯しますが、すべて青点灯が適切ですか？
> 左右間の接続に関するものが緑なのであれば、**左右接続の瞬間は緑点灯**であるべきでは？

そのとおり。**色が意味を持つと決めた以上、復帰の合図も同じ色でなければ
意味が壊れる。**分割リンクの復帰に青を使っていたのは、自分で決めた
対応表を自分で破っていた。

---

## 色の意味（これを唯一の出所とする）

| 色 | 意味する通信 | 実機の対応 |
|---|---|---|
| **青** | **ホストとの接続**（BLE プロファイル） | あり。実機の青そのもの |
| **緑** | **左右間の接続**（分割リンク） | **無い。完全分割型ゆえの追加** |
| **橙** | 電池 | あり |

**この対応は絶対に混ぜない。**点滅・点灯・復帰の合図、すべてこの色で出す。

## 点滅の速さ（実機に倣う）

| 速さ | 意味 |
|---|---|
| **1 秒に 4 回**（速い） | **未ボンド。**相手を知らない＝ペアリングを待っている |
| **1 秒に 2 回**（遅い） | **ボンド済みだが未接続。**相手は知っていて、探している／待っている |
| 点灯 1 秒 → 消灯 | **繋がった合図** |
| 消灯 | 繋がっている（**実機も接続中は消灯**） |

実機の状態表（P3PC-6641-05）:
- 青色点滅（1 秒に **4** 回）＝ ペアリング**モード**（未登録）
- 青色点滅（1 秒に **2** 回）＝ ペアリング**待機**モード（登録済み）

**当初 4 回を実装していなかった。**「ZMK に広告中の事象が無い」を理由に
2 回へ寄せたが、**ボンド状態は公開 API で取れるので区別できた**。
区別できたのに区別しなかった、というのが正確なところ。

---

## 状態の全列挙（**ここが本題**）

### 左（セントラル）

ホストと分割の 2 つを**独立に**持つ。両方未接続なら**交互に出す**
（利用者の判断。片方だけ出すと、もう片方の異常が見えない）。

| # | 分割リンク | ホスト | 表示 |
|---|---|---|---|
| L1 | 未ボンド | 未ボンド | **緑 4 回 ⇄ 青 4 回 を交互**（★出荷直後） |
| L2 | 未ボンド | ボンド済み・未接続 | 緑 4 回 ⇄ 青 2 回 を交互 |
| L3 | 未ボンド | 接続済み | 緑 4 回 |
| L4 | ボンド済み・未接続 | 未ボンド | 緑 2 回 ⇄ 青 4 回 を交互 |
| L5 | ボンド済み・未接続 | ボンド済み・未接続 | 緑 2 回 ⇄ 青 2 回 を交互 |
| L6 | ボンド済み・未接続 | 接続済み | 緑 2 回 |
| L7 | 接続済み | 未ボンド | 青 4 回 |
| L8 | 接続済み | ボンド済み・未接続 | 青 2 回 |
| L9 | 接続済み | 接続済み | **消灯** |
| L10 | 接続した瞬間 | — | **緑を 1 秒点灯** → 上の表へ |
| L11 | — | 接続した瞬間 | **青を 1 秒点灯** → 上の表へ |

### 右（周辺機）

**ホストとの接続を持たない。**だから**青は出ない**（起動時を除く）。

| # | 分割リンク | 表示 |
|---|---|---|
| R1 | 未ボンド | **緑 4 回**（★出荷直後） |
| R2 | ボンド済み・未接続 | 緑 2 回 |
| R3 | 接続済み | **消灯** |
| R4 | 接続した瞬間 | **緑を 1 秒点灯** → 上の表へ |

### 左右共通

| # | 状態 | 表示 |
|---|---|---|
| C1 | 起動直後 | **青を 3 秒点灯 → 消灯**（実機どおり。電源が入った合図で、通信とは無関係） |
| C2 | 電池残量が少ない | 橙 1 回点滅 / 30 秒 |
| C3 | 電池を交換 | 橙 2 回点滅 / 15 秒 |
| C4 | sleep | 消灯（GPIO が状態を保持するので、点けたまま寝ると垂れ流す） |
| C5 | idle（30 秒無操作） | **消さない。**警告が放置で消えるのは警告灯として逆 |

**優先順位**（上ほど強い）:
起動 > 電池（要交換 > 低下）> 接続の合図 > 分割・ホストの未接続 > 消灯

電池を接続より上に置くのは、**電池が尽きれば通信も無くなる**から。
根本原因の方を見せる。

## 何で判定するか（**すべて公開 API**）

| 何 | どこから |
|---|---|
| 分割リンクの接続（左） | `zmk_split_transport_central` を列挙して `api->get_status()` の `connections` |
| 分割リンクの接続（右） | `zmk_split_transport_peripheral` を列挙して同上 |
| **分割のボンド（右）** | **`zmk_split_bt_peripheral_is_bonded()`**（`zmk/split/bluetooth/peripheral.h`） |
| ホストの接続 | `zmk_ble_active_profile_is_connected()` |
| **ホストのボンド** | **`zmk_ble_active_profile_is_open()`**（真＝未登録） |
| 電池 | `zmk_battery_state_changed` の `state_of_charge` |
| 活動状態 | `zmk_activity_get_state()` |

### ⚠️ 1 つだけ取れないもの

**左から「分割相手とボンド済みか」を知る公開 API が無い。**

`central.c` に `is_bonded` に当たるものは無く、`peripherals[]` は static。
右には `zmk_split_bt_peripheral_is_bonded()` があるのに、左には対応物が無い。

**代替:** 左は `CONFIG_BT_MAX_PAIRED` のボンド一覧を
`bt_foreach_bond()` で数える手はあるが、**ホストのボンドと分割のボンドが
同じ一覧に混ざる**ので、分離するには peer アドレスの照合が要る。

**今回はここまでやらない。**左の分割は
**「未接続＝2 回点滅」に寄せる**（L1・L4 の緑を 4 回ではなく 2 回にする）。
右は `is_bonded` があるので 4 回／2 回を正しく出せる。

**この非対称は記録しておく。**出荷直後に
「左＝緑 2 回・右＝緑 4 回」という食い違いが出るが、
**どちらも『左右が繋がっていない』を意味している**ので実害は無い。
気になるなら `bt_foreach_bond()` での判定を後から足す。

## 検証

**故意に作れる状態から確かめる。**

| 状態 | 作り方 |
|---|---|
| R1（右・未ボンド） | `settings_reset` を焼いてから右のファームを焼く |
| L9 / R3（全部接続） | 普通に起動して繋がるのを待つ |
| L6（右だけ落とす） | 右の電源を切る → **左が緑 2 回** |
| L8（ホストだけ落とす） | Mac の Bluetooth を切る → **左が青 2 回** |
| L5（両方落とす） | 上の 2 つを同時に → **左が緑と青を交互** |
| R4（復帰の合図） | 右の電源を入れ直す → **繋がった瞬間に緑が 1 秒** |
| C5（idle で消えない） | 未接続のまま 1 分放置 → **点滅が続く** |
