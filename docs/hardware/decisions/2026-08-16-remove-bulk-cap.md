# 2026-08-16 バルクコンデンサ C_BULK を削除した（open-gaps #44）

**決定。**`C_BULK`（100µF・C15008・1206）を子基板から**削除**する。
実装部品が **2 個減る**（左右の子基板に 1 個ずつ）。

**⚠️ 消したのはバルクだけ。パスコン（C_DB / C_U1 / C_U2）は全部残る。**
役割が違うので、この判断はパスコンに一切影響しない（§6）。

**覆した結論**: #38「バルクは既に最小」・electrical-design 1-5
「バルクが無いと電池を使い切る前にブラウンアウトする」。
**両方とも、実測していない電流値に乗っていた。**

## 1. 何が変わったか — **実測が入った**

判定式は前から分かっていた:

```
送信中の降下 = I·R·(1 − exp(−t/(R·C)))
C→0 の上界  = I·R          ← **容量が何であっても、これが上限**
余裕        = _RAIL_FLOOR 2.00V − MCU_V_MIN 1.70V = 300mV
```

`(1 − exp(...))` は必ず 1 以下なので、**降下は `I·R` を超えない。**
これは **`C = 0`・`t = ∞` の最悪ケース**の値で、容量にもバースト長にも依らない。

つまり **`I·R` が 300mV に収まるなら、容量はゼロでよい。**
破綻点は `300mV ÷ 9.2Ω = 32.6mA`。

### ⚠️ 判定の順序 — **時間軸は `I·R` が足りないときにだけ意味を持つ**

```
1. C を一切考えず I·R を計算する
      ↓ 余裕に収まる？
      ├ YES → 【終わり】容量ゼロでよい。τ もバースト長も問う必要なし  ← 今回
      └ NO
2. ここで初めて τ = R·C を考える。バースト長を覆う C = バースト長 ÷ R
      ├ 現実的なサイズ → 載せる
      └ 非現実的       → バルクでは解決しない。
                        R を下げる／昇圧する／I を下げる のいずれか
```

**この順序を踏み外すと「バースト 31ms ＞ τ 920µs だから容量を増やすべきだ」
という誤った結論に行き着く。**C を増やして得られるのは「`I·R` に到達する
までの時間を延ばす」ことだけで、**`I·R` 自体が許容できるなら価値が無い。**

### 元の 100µF は、どちらに転んでも意味を持たなかった

| もし | 100µF は |
|---|---|
| `I·R` が足りている（＝実際） | **不要** |
| `I·R` が足りないとして | バースト 31ms を覆うには `31ms ÷ 9.2Ω ≈ 3400µF` 必要。**100µF では最初の 1ms 弱しか支えられず役不足** |

出典なしの `BLE_TX_CURRENT = 15mA` に乗って選ばれた値だったことの帰結。

| 値 | 出所 | 状態 |
|---|---|---|
| R = 9.2Ω | 2026-08-11 実測（1.07V/本・打ち止めより下＝保守側） | **確定** |
| 余裕 300mV | ソケット 2V min ＋ nRF52840 1.7V（データシート 2 枚） | **確定** |
| **I** | **`BLE_TX_CURRENT = 15mA`** | **⚠️ [暫定]・出典なし** |

**分かっていなかったのは電流だけだった。**しかも 15mA には
データシートの引用も測定も無く、**誰かが推測で書いた数字が設計の
根拠になっていた**（`provisional-values.md` にも「オシロが要る・未測定」と
明記されていた）。

**2026-08-16 に測った。**

## 2. 実測（DS1104Z・2 回）

### 測定条件

```
マンガン単3×2（開放 3.00V）
   ＋ ──────────────── XIAO の 3V3 パッド
   − ──┬── 10Ω ────── XIAO の GND パッド
       │      │
   GNDクリップ  プローブ先端（ローサイド）
```

- **USB は挿さない**（挿すと基板上の LDO 経由で給電されシャントを迂回する）
- **バルクは付けない**（付けるとバーストを吸って見えなくなる）
- **安定化電源も使わない**（出力の平滑 220µF が同じことをする）
- 測定用ファーム `c4_txburst`（**LED を明示的に消灯**・§5）

**ローサイドにした理由**（測定側の判断・こちらも検算した）:
ハイサイドの A−B 演算だと同相 3.0V を収めるため 500mV/div が要り、
8bit で **1LSB ≈ 2.2mA**。ローサイドなら 50mV/div が使えて **0.2mA**。
**10 倍以上の分解能差。**差動プローブが無い以上、ローサイド一択。

### 結果

| | 1 回目（広告のみ） | **2 回目（広告＋スキャン）** |
|---|---|---|
| ピーク（baseline 補正後） | 8.02mA | **10.22mA（+27%）** |
| バースト長 | 0.85〜2.3ms | 1.2〜31ms |
| 量子化ステップ | 2.004mV（0.2mA） | 同じ |
| 記録 | 120 万点 / 200ns | **600 万点 / 40ns / 240ms** |

**独立取得で 10.220mA が完全に再現。**飽和なし（上位が離散値）。

### ⚠️ 1 回目は測定条件が間違っていた（**利用者の指摘で判明**）

1 回目はこちらが `CONFIG_ZMK_SPLIT=n` を指定した。「ピークの高さは
送信理由によらないはず」という**こちらの推論**で、実測ではなかった。

> **バルクの役割は、電流の最大瞬間風速でも耐えるためですよね？**

**そのとおりだった。**分割セントラルは「ホストへ広告（TX）」と
「右をスキャン（RX）」を**同時にやる**。TX は PA、スキャンは LNA と
**別の回路が動く**ので、重なると電流は**足し算**になる。
**そこが最大瞬間風速で、それを測定条件から外していた。**

→ 分割セントラルで測り直したら **27% 上がった**。指摘が正しかった。

## 3. 全数走査 — **10.22mA が上界であることの裏づけ**

### 10.22mA とは何の値か

```
実測波形（40ns サンプル）
   ├→ 200ns 幅の移動中央値 ───→ 包絡線。その最大値 = 10.22mA  ← §4 で使う
   └→ 実測 − 包絡線 ─────────→ 残差。その最大値 = 1.40mA
```

**平均値ではない**（平均はスリープ主体で 0.5mA 程度）。
**生サンプルの最大値でもない。**
**「200ns 以上持続する電流の最大値」**であり、`I·R` に入れるべきはこの量。
電池の内部抵抗による降下は、電流が**持続する**ときに問題になるため。

### 残差の全数走査

```
1ns 分解能・600µs 窓・60 万点を全数走査
（200ns 局所中央値からの逸脱を全点で評価）

  最大逸脱   1.40mA（独立検算では 1.60mA。差は量子化ステップ 0.2mA の 1 段分
             ＝ 別実装が 1LSB 以内で一致した、というのが結論）
```

**これが保証しているのは「包絡線 10.22mA の上に、隠れた持続的な段が無い」こと。**
ピーク 10.22mA は「約 20µs かけて緩やかに上る包絡線の頂点」であって、
その上に細いパルスは乗っていなかった。

仮に残差を丸ごと足して 11.62mA としても `× 9.2Ω = 107mV` で、
**破綻点 32.6mA に対してまだ 2.8 倍**。残差は判断に効かない。

> ⚠️ **旧記述の訂正（2026-08-16）。**この節は当初
> 「**µs 級の尖りが無い＝バルクが守る相手が実在しなかった**」と書いていたが、
> **誇張だった。**この走査が示すのは上記のとおり「§4 で使うピーク値の
> 信頼性」であって、バルクの存在理由そのものの否定ではない。
> バルクが不要な理由は §1 の判定順序と §4 の `I·R` に尽きる。
>
> また当初は閾値を「**2mA 超のスパイク 0 個**」と書いていたが、
> **2mA は量子化ステップ 0.2mA の 10 倍という便宜的な線で、物理的な根拠が無い。**
> 意味のある比較は**破綻点 32.6mA との比**（残差 1.4〜1.6mA は 1/20 以下）。

### 帯域の但し書き（測定側の申告・そのまま採る）

1X プローブの帯域（6〜10MHz）が上限なので、**35〜60ns より速い成分は
原理的に見えていない**。ただし 10X（100MHz+）でも量子化ノイズ以上の
尖りは出なかったため、見逃した鋭いピークがある可能性は低い。
**断定はしない。**

> ⚠️ **この限界は、バルクの要否には効かない。**
> 100µF/1206 の自己共振は**約 0.5MHz**で、それより上では ESL 支配になり
> コンデンサとして振る舞わない。**35ns 級はそもそもバルクの担当外**
> （パスコンの領域・自己共振 約 19MHz。§6）。
> プローブ帯域が効くとしたら**パスコン側の議論**であって、この文書の
> 結論には影響しない。

## 4. 判定

```
10.22mA × 9.2Ω = 94mV
余裕 300mV に対して 31%     → **安全率 3.2 倍**
破綻点 32.6mA まで          → **3.2 倍**
```

**容量ゼロでも、94mV しか落ちない。**

### baseline の不確かさは効かない

測定側は「真のゼロを実測していない（最頻値 −4.008mV を使用）」と
申告している。**切り離しての実測は依頼しなかった。**理由:

| baseline | ピーク |
|---|---|
| −4.008mV（採用） | 10.22mA |
| 0mV（最も楽観） | 9.82mA |
| −8mV（最も保守） | 10.62mA |

**振れ幅 ±0.4mA に対して、破綻点まで 22mA の余裕。**
安全率が 3.2 → 3.1 倍になる程度で、判断は動かない。
**測定者の時間を使う価値が無い。**

## 5. 測定を成立させるために作ったもの

> ⚠️ **この節のファイルは main に入れていない**（2026-08-16 の判断）。
> **測定専用で、本番のキーボードには一切関係しない**ため
> （`build.yaml` に載せると push のたびに CI がビルドし続ける）。
>
> **置き場所: ブランチ `meas/c4-txburst`**
>
> ```
> git checkout meas/c4-txburst
>   firmware/src/led_force_off.c            LED を起動直後に消灯へ固定
>   firmware/Kconfig                        CONFIG_HHKB_LED_FORCE_OFF
>   config/boards/shields/c4_txburst/       測定専用シールド
>   tools/check_zmk_config.py               kscan-mock を読めるようにした
> ```
>
> **再測定するときは、このブランチを push すれば CI が `.uf2` を作る**
> （`c4_txburst-xiao_ble__zmk-zmk.uf2`）。**消さないこと。**

### ⚠️ LED が測定を汚す（**利用者の指摘**）

> LED がつく FW なので、電流量が正しく測れないと思います

**そのとおりだった。**XIAO の RGB LED は**共通アノードで 3V3 に直結**
（回路図 Seeed XIAO nRF52840 v1.1・RGB1）。3V3 パッドへ注入した電流が
**LED を通る経路を持つ**。1 色 1〜2mA ＝ **測りたい 10mA と同じ桁**。

しかも未接続だと青と緑が 1 秒に 2 回点滅する条件（status_led.c の状態表）。
**必ず邪魔になる。**

### `CONFIG_HHKB_STATUS_LED=n` では足りなかった

それは `status_led.c` を**ビルドしないだけ**で、**ピンを消灯側へ駆動
しない**。未初期化 GPIO は入力ハイインピーダンスなので消えている
「はず」だが、**それは推測**（CLAUDE.md 5「設定しただけでは効いていない」）。

→ `firmware/src/led_force_off.c` を作り、**起動直後に 3 本とも明示的に
消灯へ駆動**した（`CONFIG_HHKB_LED_FORCE_OFF`）。
`status_led.c` の `#else` にできないのは、CMakeLists が ifdef で
ファイルごと外すため（無効時は到達しない）。

**そのうえで実機で目視確認した**（消えていた）。

### 測定専用シールド `c4_txburst`

走査電流をゼロにするため `kscan-mock` を使い、ログ・UART 宣言・ADC を
外した（それぞれ +0.44mA / +0.46mA / 段 が乗ることが実測で分かっている）。

⚠️ **1 回目でファーム同定に失敗した**（報告に「起動後 60 秒でスリープする
firmware」とあったが、この治具は 30 分。60 秒は古い `proto_split_left`）。
→ 2 回目は広告名を `c4txburst v2` にして見分けられるようにした。

## 6. パスコンは残る（**役割が違う。混同しないこと**）

> ### ⚠️ 2026-08-16 追記 — **`C_DB` はこの後、別の理由で削除された**
>
> **この節の「役割が違う」は今も有効**だが、**「パスコンは全部残る」は
> 覆った。**同じ日に `C_DB` を削除している（open-gaps #45・
> [2026-08-16-cdb-has-no-local-load.md](2026-08-16-cdb-has-no-local-load.md)）。
>
> **理由はこの文書の測定とは無関係。**バルクを消したのは「守る相手の
> 電流が実在しなかった」から。C_DB を消したのは**トポロジ**——3V3 の
> 負荷が 2 つとも子基板の外にいて、どちらも自分の直近に別のパスコンを
> 持っていた（nRF52840 → XIAO 内蔵 2.2µF ×5、595 → C_U1/C_U2）。
>
> **いま残るパスコンは主基板の `C_U1` / `C_U2` だけ**（左 1・右 2）。
> **子基板にコンデンサは 1 つも無い。**

| | バルク（削除） | **パスコン** |
|---|---|---|
| 部品 | C_BULK 100µF/1206 | ~~C_DB 0.1µF ×2~~ / C_U1 ×2 / C_U2 ×1 |
| 相手 | 電池の内部抵抗による**電圧降下** | IC が切り替わる瞬間の**高周波ノイズ** |
| 時間 | µs〜ms | **ns** |
| 自己共振 | 約 0.5MHz | 約 19MHz |
| 置き場所 | レールのどこでもよい | **その IC の電源ピン直近**（ループ長で効く） |
| 今回の測定 | **これを否定した** | **何も言っていない** |

**今回測ったのは「電池がどれだけ電圧を保てるか」。**パスコンが相手に
しているのは 74LVC595 が 16 本の出力を同時に切り替えた瞬間のノイズで、
**測定の対象外**。40ns 分解能では ns 級の現象は原理的に見えない。

**測っていないものについては何も言えない**ので、パスコンは触らない。

#38 の「バルクとパスコンは兼ねられない・役割が違う」は**いまも有効**。
変わったのは「µs 級を担当する相手が実在しなかった」という事実のほうで、
**バルク側が消えた。パスコンが要る理由は無傷。**

## 10. 残るもの・限界（**正直に書く**）

測定側の申告と、こちらの検算で残った不確かさ:

- **観測窓は合計 1 秒未満。**より稀なピークの可能性は否定できない
  （破綻点まで 3.2 倍あるので、相当に稀で大きいものでない限り効かない）
- **接続確立後の TX は未観測。**測定時は広告＋スキャン状態
- **TX / 広告 / スキャンは区別できていない。**電流波形だけでは証明
  できないため、測定側が**分類を拒否した**（正しい判断）。
  `BLE_TX_CURRENT = 10.22mA` は厳密には「**観測窓内の全イベントの
  最大値**」であって TX 単独の値ではない。**上界としては正しい**
- **単一セッション・新品電池。**温度を振った再現性は未確認
- **35〜60ns より速い成分は原理的に見えていない**（プローブ帯域）。
  ただし **この限界はバルクの要否には効かない**（§3 末尾・自己共振 0.5MHz）
- **広告名 `c4txburst v2` の確認**は、測定側に BLE ラジオが無いため
  未実施。**LED が消えていた**こと（旧ファームなら点滅する条件）と、
  **ピークが 8.02 → 10.22mA に上がった**こと（`SPLIT=y` が効いた証拠）が
  状況証拠

**戻すときは再配線が要る**（部品を消したので配線が変わった）。
戻す判断に至ったら、この記録と #44 を読み直すこと。

## 11. この結論は本システム固有か（**他所へ持ち出すとき**）

`I ≈ 10mA` は BLE 由来なので**システムに依らずほぼ普遍**。
一方 **破綻点は `余裕 ÷ R` で決まる**ので、支配的なのは **R（電源の内部抵抗）**:

| 電源 | R の目安 | 10mA での降下 |
|---|---|---|
| リポ／リチウムイオン／LDO 出力 | ≪1Ω | **数 mV**（誤差） |
| アルカリ 単3 ×2（新品） | 0.3〜1Ω | 3〜10mV |
| **マンガン 単3 ×2（打ち止め付近）** | **9.2Ω** ← 今回 | **94mV** |
| コイン電池 CR2032 | 10〜100Ω | 0.1〜1V |

**94mV というそこそこの数字が出たのは、乾電池を打ち止めまで使い切る前提だから。**
リポや LDO ならこの議論自体が起きない。

### ⚠️ 「余裕が少ないシステムなら大容量が要る」は成り立たない

**バルクで解けるゾーンは非常に狭い。**§1 の順序で 2 まで進んでも、
`必要な C = バースト長 ÷ R` なので:

| R | 破綻点（余裕 300mV） | 31ms を覆う C | 判定 |
|---|---|---|---|
| 0.5Ω（リポ） | 600mA | 62000µF | **手順 1 で終わる**（10mA は余裕） |
| 9.2Ω（今回） | 32.6mA | 3400µF | **手順 1 で終わる** |
| 50Ω（CR2032） | 6mA | 620µF | **手順 2 へ。C が現実的** ← 唯一 |

- **R が小さい** → `I·R` 自体が問題にならないので C は不要
- **R が大きい** → 必要な C が小さくて済む

**バルクが本当に効くのは「高抵抗かつ低電流」（CR2032 級）だけ。**
CR2032 の BLE モジュールに 100〜470µF が載っているのはこの理由。

余裕そのものが足りないときの定石は、効く順に:

1. **R を下げる**（並列本数・低 ESR 品・電池の種類）← 最も効く
2. **余裕を広げる**（昇圧 DC-DC でレールを固定 ⇒ 余裕が実質無限）
3. **I を下げる**（TX 出力・広告間隔・スキャンと TX を重ねない）
4. **C を足す** ← 上の狭いゾーンに入っているときだけ
