# XIAO の LED で実機の LED インジケーターを再現する（2026-08-16）

## これは新機能ではない

**実機 HHKB Professional HYBRID には前面に LED インジケーターがある。**
この案件は長らくその事実を記録しておらず、次のように書いていた:

- `docs/superpowers/specs/2026-08-04-hhkb-split-keyboard-design.md`
  「RGB、OLED、…**HHKB に存在しない**独自レイヤー」
- `docs/superpowers/plans/2026-08-05-phaseC-electrical-firmware-validation.md`
  「HHKB に存在しない機能（RGB / OLED / …）は最終ファームに入れない」

**LED を RGB と同じ箱に入れていたのが誤り。**キーの下を光らせる RGB は実機に
無いが、**状態表示の LED は実機にある**。よって:

> **LED を足すことが実機再現からの逸脱なのではない。
> LED が無いことが実機との差だった。**

利用者の指摘（「いや HHKB に LED ありますけどね」）で判明した。
CLAUDE.md の「**差があること自体は悪くない。気づけないことが悪い**」に当たる型。

## 実機の状態表（一次情報）

出典: PFU『Happy Hacking Keyboard 取扱説明書』**P3PC-6641-05**（2023 年 6 月）
https://origin.pfultd.com/downloads/hhkb/manual/P3PC-6641-05.pdf

| LED の状態 | 意味 |
|---|---|
| **消灯** | **接続モード** / OFF モード |
| 青色点滅（1 秒に 2 回） | ペアリング待機モード |
| 青色点滅（1 秒に 4 回） | ペアリングモード |
| 青色点灯 | 接続待機モード |
| 橙色 1 回点滅を 30 秒間隔 | 電池残量が少ない |
| 橙色 2 回点滅を 15 秒間隔 | 電池を交換 |

本文より: 電源オン →「青色に点灯したあと、消灯」。
電源オフ →「橙色点灯→消灯」。接続完了時 →「消灯」。

**設計上いちばん効く事実: 接続中は「消灯」が正しい。**
常時点灯ではないので、乾電池 2 本でも電流を心配しなくてよい
（実機も同じ理由でこうしていると考えられる）。

WebFetch では PDF を解析できず、`pdftotext -layout` で本文から抽出した。

## 決めたこと

### 1. XIAO の LED は「3 個」ではなく「RGB 1 個」

Seeed Studio Wiki（https://wiki.seeedstudio.com/XIAO_BLE/）より
**"3-in-one LED (User LED)"** — 赤 P0.26 / 緑 P0.30 / 青 P0.06 が
**1 パッケージの共通アノード**。別に Charge LED（P0.17）があるが使わない。

**これは設計に効く。**1 個なので**赤+緑を同時に点けると同じ一点が橙色に光る**。
3 個離れていたら 2 箇所が光るだけで橙には見えない。
→ 実機の「青と橙」を**1 つの窓で**再現できる。

### 2. 実機に無い状態を 1 つ足す（**完全分割型ゆえ**）

実機は一体型なので、状態表に「**右手と繋がっているか**」が無い。
だが左手は独立した 2 つの接続を持つ:

| 接続 | 実機の対応 | 扱い |
|---|---|---|
| ホストへの広告・接続 | あり（青） | 実機どおり |
| **右手のスキャン・接続** | **無い** | **緑を当てる** |

右手が落ちると利用者から見て「**キーの右半分が反応しない**」という
最も切実な故障になる。ここに表示が無いのは実用上まずい。

**緑は「ホスト未接続」より優先する。**キーの半分が死ぬ方が切実だから。

### 3. 左手が右手の接続状態を知る方法（**公開 API だけで完結**）

調べた順に:

- `zmk_split_peripheral_status_changed` を raise しているのは
  **`app/src/split/bluetooth/peripheral.c`（右手側）**。
  `central.c` には 1 箇所も無い。**当初の見込みと逆だった**
- `central.c` の `peripherals[]` は **`static`**。外から見えない
- `app/include/zmk/split/central.h` に接続状態を返す関数は無い
  （あるのは `invoke_behavior` / `update_hid_indicator` /
  `get_peripheral_battery_level` のみ）

**解:** transport 層は `ZMK_SPLIT_TRANSPORT_CENTRAL_REGISTER` =
`STRUCT_SECTION_ITERABLE_NAMED` で登録されているので列挙できる。

```c
STRUCT_SECTION_FOREACH(zmk_split_transport_central, t) {
    struct zmk_split_transport_status st = t->api->get_status();
    /* st.connections: DISCONNECTED / SOME_CONNECTED / ALL_CONNECTED */
}
```

**内部 static には触らない。**`tools/test_firmware.py` が
`peripherals[` を実コードから grep して守っている
（ZMK の更新で無言で壊れるのを防ぐため）。

### 4. Zephyr の LED サブシステムではなく raw GPIO

`CONFIG_LED` / `CONFIG_LED_GPIO` を増やさずに済む。
`GPIO_ACTIVE_LOW` は devicetree 側が持つので**コードに極性を書かない**。
**PWM は使わない**（`CONFIG_PWM` と HF クロックを抱えるため）。

### 5. idle / sleep では必ず消す

**点いたまま寝ると GPIO はその状態を保持する。**30 分ぶん 1〜2mA を
垂れ流すので、寝ない方がマシになる。`zmk_activity_state_changed` で消す。

## 実装した表示

**上ほど優先。**同時に複数成立しうるので 1 つに畳んでから点ける
（状態ごとに別の work を走らせると競合して色が混ざる）。

| 状態 | 色 | パターン | 実機の対応 |
|---|---|---|---|
| 起動直後 | 青 | 点灯 3 秒 → 消灯 | **実機どおり** |
| 電池交換（≤5%） | 橙 | 2 回点滅 / 15 秒 | **実機どおり** |
| 電池低下（≤15%） | 橙 | 1 回点滅 / 30 秒 | **実機どおり** |
| **右手と繋がっていない** | **緑** | 1 秒に 2 回 | **実機に無い・分割型固有** |
| ホストと繋がっていない | 青 | 1 秒に 2 回 | 実機のペアリング待機相当 |
| 接続中 | — | **消灯** | **実機どおり** |
| idle / sleep | — | 消灯 | — |

右（周辺機）はホストとの接続を持たないので青の点滅は出ない。
緑・橙・起動時の青点灯のみ。

## 割り切ったこと

**ZMK に「広告中」「スキャン中」の事象は無い。**
広告もスキャンも `central.c` と `ble.c` の内部に閉じていて、
イベントマネージャに出てこない。よって
**「繋がっていない」を広告／ペアリング待機の代理として使っている。**
実機の状態表とは意味が厳密には一致しない。

実機の「1 秒に 4 回（ペアリングモード）」と「1 秒に 2 回（ペアリング待機）」の
区別も、この理由で出せない。**2 回の方に寄せた。**

## まだ終わっていないこと

⚠️ **XIAO 基板上の LED はケースの中で見えない。**
実機再現としては**未完成**で、上ケースの窓か導光、または外付け LED
（D4 / D9 が空いている）が要る。今回は利用者の指示でファームのみ。
→ `open-gaps.md` に記録した。

⚠️ **実機の LED が部品表にもケース CAD にも無い。**
`parts-audit.md` に LED も導光も無く、ケースの開口は USB-C と
電源スイッチだけ。

⚠️ **LED 点灯時の電流を実測していない。**接続中は消灯なので定常状態では
効かないが、未接続で放置すると乗る。→ `provisional-values.md`。
